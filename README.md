# Market Truffler 🐷🍄

A crypto trading system, currently at its **foundation milestone**: a clean,
containerized, runnable application shell — authentication, a database, a
typed API, and a navigable frontend. No trading logic, no market data, no
exchange connectivity yet. See [`docs/ARCHITECTURE.md`](docs/ARCHITECTURE.md)
for where this is headed.

## Repository structure

```
market-truffler/
├── apps/
│   ├── api/            FastAPI backend (Python 3.13, SQLAlchemy 2, Alembic)
│   └── web/             Next.js frontend (TypeScript, Tailwind, shadcn/ui)
├── research/
│   └── oink_corp/       🧬 OINK CORP — reserved boundary for future strategy research
├── packages/
│   └── shared/           Reserved boundary for future code shared across apps
├── infra/                 Reserved boundary for future non-app infrastructure
├── docs/
│   └── ARCHITECTURE.md    Conceptual system architecture (future + current)
├── docker-compose.yml
└── .env.example
```

`research/oink_corp`, `packages/shared`, and `infra` are intentionally empty
except for a README explaining their purpose — they exist as boundaries so
future work has an obvious home without restructuring the repo, not because
anything lives there yet.

## What's real in this milestone

Docker Compose, containers, the Next.js frontend, the FastAPI backend,
PostgreSQL, database migrations, authentication (login/logout, hashed
passwords, sessions that survive a refresh), protected routes, frontend ↔
backend ↔ database communication, health/readiness checks, structured
logging, and tests.

What's **not** real: any Bybit/exchange connectivity, market data, features,
scoring, rankings, or trading logic. Sniffer, Warhog, and OINK CORP are
reachable in the UI and each show a deliberate "in progress" page. Vitals
(system health)'s SYSTEM section is real; its MARKET/Sniffer/Warhog/OINK CORP
sections are laid out for the future but every value in them is an honest
"N/A" — nothing is simulated.

## Prerequisites

- Docker and Docker Compose
- (Optional, for running things outside Docker) Python 3.13 and Node.js 22+

## 1. Configure environment

```bash
cp .env.example .env
```

Then set `SESSION_SECRET` to a real random value — the API refuses to start
without one:

```bash
python3 -c "import secrets; print(secrets.token_urlsafe(48))"
```

Paste the output as `SESSION_SECRET` in `.env`. Nothing else in
`.env.example` needs to change for local development. No exchange
credentials are needed anywhere — this milestone doesn't talk to Bybit or
any other exchange.

## 2. Build and start

```bash
docker compose up --build
```

This starts three services:

| Service    | What it is                          | Port  |
|------------|--------------------------------------|-------|
| `postgres` | PostgreSQL 17                        | internal only |
| `api`      | FastAPI backend                      | `localhost:8000` |
| `web`      | Next.js frontend                     | `localhost:3000` |

`postgres` has no published port — it's reachable only from `api`, on the
internal Docker network, never from the host or the internet. `web` and
`api` wait on each other's health checks (`depends_on: condition:
service_healthy`), so there's no arbitrary `sleep`-based startup choreography.

## 3. Migrations

**Migrations run automatically.** The `api` container's entrypoint
([`apps/api/docker-entrypoint.sh`](apps/api/docker-entrypoint.sh)) runs
`alembic upgrade head` before starting the server, every time the container
starts. This is the deliberate execution strategy for this milestone: a
single API replica, so there's no risk of concurrent migration races, and no
manual migration step to forget.

To run migrations manually (e.g. against a container that's already up):

```bash
docker compose exec api alembic upgrade head
```

To create a new migration after changing a model:

```bash
docker compose exec api alembic revision --autogenerate -m "describe the change"
```

Autogenerated migrations are reviewed and committed like any other code
change — they are not applied blindly.

## 4. Create the first user

There's no self-service sign-up (an intentional, minimal-auth design for
this milestone). Create a user with the bundled script:

```bash
docker compose exec api python -m app.scripts.create_user you@example.com "a-strong-password"
```

Running it again with the same email updates that user's password instead
of failing.

## 5. Log in

Open [http://localhost:3000](http://localhost:3000). You'll be redirected to
`/login`. Sign in with the credentials you just created. The session is a
signed, `httpOnly` cookie — it survives a page refresh and is enforced on
both the frontend (redirects) and the backend (every protected endpoint
independently verifies it).

From there you can navigate to Home, Sniffer, Warhog, OINK CORP, and Vitals.
Sniffer, Warhog, and OINK CORP each show an intentional "in progress" page.
Vitals shows a SYSTEM section with live operational status (API liveness,
API readiness, database connectivity, uptime, environment, backend version),
plus MARKET/🐽 SNIFFER/🐗 WARHOG/🧬 OINK CORP sections previewing what
Vitals will eventually report on — every row in those is an honest "N/A",
never a fabricated value, since none of that infrastructure exists yet.

## 6. Run tests

Backend:

```bash
cd apps/api
python3 -m venv .venv && source .venv/bin/activate
pip install -e ".[dev]"
pytest
```

Frontend:

```bash
cd apps/web
npm install
npm test
```

Both suites also run without Docker running — the backend tests use an
in-memory SQLite database, not the real Postgres container.

## 7. Lint and type-check

```bash
# Backend
cd apps/api && ruff check app tests && mypy app

# Frontend
cd apps/web && npm run lint && npm run typecheck
```

## 8. Stop the environment

```bash
docker compose down
```

Data persists in the `postgres_data` Docker volume across `down`/`up` cycles
and container restarts.

## 9. Reset the development environment

To wipe the database and start clean (irreversible — deletes all local data):

```bash
docker compose down -v
docker compose up --build
```

Then re-run the migration/user-creation steps above (migrations run
automatically on startup; you'll still need to re-create your user).

## Local development without Docker

Each app documents its own local-dev environment variables in its own
`.env.example` (`apps/api/.env.example`, `apps/web/.env.example`) for
running the API with `uvicorn --reload` or the frontend with `npm run dev`
directly on the host, against a Postgres you run yourself. This is optional
— Docker Compose is the primary, documented path.

## Design notes worth knowing

- **Auth**: sessions are a signed JWT in an `httpOnly`, `SameSite=Lax`
  cookie — no server-side session table. Stateless by design for this
  milestone: logout tells the browser to delete the cookie, but the token
  itself isn't revoked server-side, so a copy of it (if somehow captured)
  would remain valid until `SESSION_TTL_MINUTES` expires. A deliberate
  simplicity trade-off for this milestone, documented here rather than
  hidden.
- **Frontend ↔ backend**: the browser only ever talks to the Next.js origin.
  A runtime route handler (`apps/web/src/app/api/[...path]/route.ts`) proxies
  `/api/*` to the FastAPI backend server-side, forwarding cookies both ways.
  This avoids CORS entirely for normal use and means the backend's internal
  URL (`http://api:8000` in Docker, `http://localhost:8000` locally) is read
  at request time, not baked into the frontend build.
- **Route protection**: `apps/web/src/proxy.ts` does a fast,
  cookie-presence-only redirect for UX. The real enforcement is server-side —
  `apps/web/src/app/(protected)/layout.tsx` calls the backend on every
  request before rendering, and every backend endpoint independently checks
  the session.
